2. KIẾN TRÚC TỔNG QUAN
--------------------------------------------------------------------------------
  Next.js (App Router, RSC)
    ├─ Server Components: đọc dữ liệu trực tiếp qua Supabase server client
    ├─ Server Actions: mutation (thêm/sửa/xóa giao dịch) — validate bằng Zod
    ├─ Route Handlers: webhook / import CSV / export
    └─ Client Components: form, biểu đồ, optimistic UI

  Supabase
    ├─ Postgres: nguồn chân lý duy nhất, business logic ở DB
    ├─ Auth: session qua cookie (@supabase/ssr)
    ├─ RLS: chính sách bảo mật ở mọi bảng
    ├─ Functions/Triggers: tính số dư, audit, validate
    ├─ pg_cron: recurring + refresh materialized view
    └─ Edge Functions: parse CSV, tác vụ nặng/bất đồng bộ

  Nguyên tắc: TIỀN và LOGIC tính toán nằm ở Postgres.
              Next.js chủ yếu là tầng trình bày + orchestration.
              KHÔNG cần API key bên ngoài cho MVP.

4. DATA MODEL (phác thảo schema)
--------------------------------------------------------------------------------
profiles
  id            uuid PK  -> auth.users.id
  display_name  text
  base_currency text     -- ví dụ 'VND', dùng để quy đổi báo cáo
  created_at    timestamptz

accounts
  id            uuid PK
  user_id       uuid     -> auth.users.id   (RLS theo cột này)
  name          text
  type          text     -- cash | bank | credit | savings | investment
  currency      text     -- 'VND' | 'USD'...
  archived      boolean default false
  created_at    timestamptz

categories
  id            uuid PK
  user_id       uuid
  name          text
  kind          text     -- income | expense
  parent_id     uuid null -> categories.id   (danh mục cha/con)
  color         text

transactions
  id            uuid PK
  user_id       uuid
  account_id    uuid     -> accounts.id
  category_id   uuid null-> categories.id
  type          text     -- income | expense | transfer
  amount        numeric(20,4)  -- luôn DƯƠNG; chiều tính theo type
  currency      text
  fx_rate       numeric  -- tỷ giá về base_currency tại thời điểm GD (snapshot)
  occurred_at   timestamptz
  note          text
  transfer_id   uuid null -- ghép 2 dòng của 1 lệnh chuyển khoản
  created_at    timestamptz

budgets
  id            uuid PK
  user_id       uuid
  category_id   uuid
  period        text     -- 'monthly'
  month         date     -- mốc đầu tháng
  amount        numeric(20,4)

recurring_rules            (giai đoạn 2)
  id, user_id, template (jsonb), rrule text, next_run date, active boolean

exchange_rates             (giai đoạn 2)
  base, quote, rate, as_of date

audit_log                  (giai đoạn 2)
  id, user_id, table_name, row_id, action, diff jsonb, at timestamptz

VIEW account_balances      -- số dư mỗi account, tính từ transactions (KHÔNG cột stored)
VIEW monthly_cashflow      -- thu/chi theo tháng
MATERIALIZED VIEW category_spend_monthly  -- báo cáo nặng, refresh định kỳ

Quy ước: transfer = 2 dòng transactions cùng transfer_id (1 expense ở account
nguồn, 1 income ở account đích) -> số dư luôn cân.

5. BẢO MẬT / RLS (bắt buộc, làm ngay từ đầu)
--------------------------------------------------------------------------------
- Bật RLS trên MỌI bảng có user_id.
- Policy mẫu: USING (auth.uid() = user_id) cho SELECT/INSERT/UPDATE/DELETE.
- Không bao giờ expose service_role key ra client.
- Server Actions validate bằng Zod TRƯỚC khi chạm DB.
- Ràng buộc ở DB: CHECK amount > 0; FK; UNIQUE; NOT NULL — không phó mặc app.
- Trigger validate: transaction.currency phải khớp account.currency.
- Test RLS bằng pgTAP / script: user A không đọc được dữ liệu user B.

9b. KIẾN TRÚC FRONTEND (ĐÃ CHỐT) — Pattern C: Hybrid
--------------------------------------------------------------------------------
Tổng thể: RSC prefetch -> React Query hydrate; Server Actions làm mutationFn.

  RSC: fetch + prefetchQuery ─► HydrationBoundary ─► Client useQuery (no spinner)
  RHF + Form ─► useMutation({ mutationFn: serverAction }) ─Zod─► Supabase
        │                          │
   optimistic update          onSettled: invalidateQueries / revalidatePath

Vì sao Pattern C:
  - Initial load nhanh như RSC (không waterfall), KHÔNG cần viết API route —
    Server Action thay thế, type-safe end-to-end.
  - React Query lo cache / optimistic / realtime ở client.
  - Một schema Zod dùng chung cho RHF + Server Action (validate 1 định nghĩa).
  - Logic tiền ở DB / Server Action; client chỉ orchestrate -> đúng tinh thần senior.

Pattern phụ trợ (áp dụng toàn bộ):
  1. Data Access Layer: mọi query Supabase gom vào /lib/data/*.ts. RSC và
     Server Action đều gọi qua DAL — không gọi Supabase rải rác trong component.
  2. Zod là nguồn chân lý: /lib/validations/*.ts. RHF dùng zodResolver, Server
     Action dùng .parse(), TS type suy ra từ schema. Một chỗ định nghĩa.
  3. Query key factory: /lib/query-keys.ts tập trung key để invalidate nhất quán.
  4. Server Action chuẩn hóa kết quả: luôn trả
       { ok: true, data } | { ok: false, error }
     -> React Query onError/onSuccess + RHF setError xử lý gọn, không throw bừa.

9c. COMPONENT LAYER (ĐÃ CHỐT) — KHÔNG import shadcn trực tiếp
--------------------------------------------------------------------------------
NGUYÊN TẮC: app code KHÔNG BAO GIỜ import từ components/ui (shadcn primitives).
App chỉ import từ tầng bọc (design system layer) do mình kiểm soát.

Phân tầng:
  components/ui/        <- shadcn copy nguyên bản (primitives). COI NHƯ "vendor",
                           không sửa tay, không import trực tiếp ở feature code.
  components/core/      <- DESIGN SYSTEM LAYER (tầng bọc). Re-export + chuẩn hóa
                           variant, size, token, a11y. Vd: Button, Input, Dialog,
                           Card... bọc quanh shadcn. ĐÂY là API công khai duy nhất.
  components/forms/     <- Field bọc shadcn Form + RHF (vd <MoneyField/>,
                           <CategorySelect/>, <DatePickerField/>) gắn sẵn
                           zodResolver pattern, hiển thị lỗi đồng nhất.
  components/patterns/  <- block ghép sẵn cấp cao (DataTable, EmptyState,
                           PageHeader, StatCard, ConfirmDialog...).
  components/charts/    <- bọc Recharts (StatCard, CashflowChart...).
  features/*/components <- UI riêng từng feature, CHỈ dùng core/forms/patterns.

Lý do (senior signals):
  - Decoupling: đổi theme / variant / thậm chí thay shadcn về sau chỉ sửa 1 tầng.
  - Nhất quán: token, spacing, a11y, focus-state tập trung — không drift.
  - Ép kỷ luật: lint rule cấm import từ components/ui ở ngoài components/core.
  - Dễ test & document (Storybook chỉ trỏ vào tầng core/forms/patterns).

Thực thi:
  - ESLint no-restricted-imports: cấm 'components/ui/*' ngoài components/core/**.
  - cn() / cva() để định nghĩa variant ở tầng core, không lặp className ở app.
  - Thêm shadcn component mới = chạy CLI vào components/ui rồi BỌC ở components/core
    trước khi feature được phép dùng.

THỨ TỰ LÀM: dựng components/core (+ forms, patterns) TRƯỚC khi build feature.
  -> chèn vào Sprint 0/1 (xem mục 7).
